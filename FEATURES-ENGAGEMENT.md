## Why these features (one-paragraph strategy)

Zonnie today is a solo, single-session utility. Young users (18–30) pick terraces in
group chats, adopt apps that produce shareable artifacts, and delete utilities that
give no reason to return. Every feature below either (a) produces a shareable artifact
or (b) pulls a second person into the funnel. Build order = viral-loop value ÷ effort.

## Feature 1 — Sun Flex share card  ⭐ BUILD FIRST

**What:** One tap on any terrace detail sheet generates a beautiful 1080×1920
Stories-format image: terrace name, neighbourhood, big sun score, "golden until HH:MM",
sunset-gradient background matching the brand, Zonnie wordmark + "free on iOS".
Native share sheet opens with the image attached.

**Why:** People on sunny terraces already post Stories. Give them a better-looking
version that carries the brand. Every share = free acquisition.

**Implementation notes:**
- Render the card as an offscreen React Native view and capture it.
  - Preferred: `react-native-view-shot` — **CHECK if it's already in package.json /
    the installed binary.** If it is NOT in the binary, it CANNOT ship OTA.
    If no capture lib exists in the binary, flag this feature as
    "requires new binary" and stub the UI behind a feature flag now.
- Card layout: reuse the Instagram-grid visual language (sunset gradient
  `sand → mustard → peach → terracotta → cocoa`, skyline silhouette optional,
  teardrop pin with score). Fonts: Fraunces_700Bold (display), Inter (body) — already
  loaded via `@expo-google-fonts`.
- "Golden until HH:MM": compute from the existing sun timeline — last hour today where
  the terrace's score ≥ 50. Engine lives in `src/engines/` (`computeRangeScore` /
  hourly scoring). Expose a helper `goldenUntil(terraceId, date): Date | null`.
- Entry point: a share icon button on `src/components/TerraceDetailSheet.tsx`,
  next to the favourite button.
- Free feature (not Pro). It IS the marketing.
- Analytics: log share taps (a counter in a persisted Zustand store is fine for now).

**Acceptance:**
- [ ] Share button on detail sheet
- [ ] Card renders with correct score, name, golden-until time, brand styling
- [ ] iOS share sheet opens with image
- [ ] Works with already-cached data (no extra network round trip)

## Feature 2 — "Terras?" group vote  ⭐ STRATEGIC PRIORITY

**What:** User multi-selects 2–3 terraces → "Ask the group" → app generates a link
that drops into WhatsApp. Friends open a lightweight web page (no install) showing
the candidate terraces with scores + photos, tap to vote. Initiator sees results in-app.
Page carries a "get Zonnie free on iOS" CTA.

**Why:** Terrace choice is a group decision in a chat. This matches the real
job-to-be-done and makes every plan a multi-person funnel.

**Implementation notes — phased:**
- **Phase A (OTA, no backend): "share a shortlist" link.**
  - Encode the shortlist in the URL itself: `https://zonnie.app/vote#t=812,455,93&d=2026-05-30T15:00`
    (terrace IDs + visit window). No server state needed.
  - Static page hosted on the existing GitHub Pages repo (`ajspilsbury87-cloud/zonnie-`):
    a single `vote.html` that reads the hash and renders the terraces from a small
    published JSON snapshot (`terraces-lite.json`: id, name, neighbourhood, lat/lng,
    orientation — generated by a build script from the app's data; **NO Google API key
    in the page**).
  - Voting in Phase A = friends reply in the chat like normal humans; the page is the
    visual aid. Zero backend, ships this week.
  - In-app: multi-select mode on `TerraceList`/map → "Share shortlist" → builds URL →
    `Share.share()`.
- **Phase B (needs tiny backend, later):** real vote counts. Cloudflare Worker + KV
  (free tier) with `POST /vote {pollId, terraceId}` and `GET /poll/:id`. Poll created
  from the app. Keep anonymous, no accounts. Out of scope for the first PR — leave a
  `// TODO(phase-b)` seam.
- Deep link: register `zonnie://terrace/:id` route handling so the web page's "open in
  app" works for installed users (check `app.config.ts` `scheme` — add if missing;
  **scheme changes need a new binary**, so if absent, the web page links to the App
  Store only for now).

**Acceptance (Phase A):**
- [ ] Multi-select up to 3 terraces in list or map
- [ ] Generates hash-encoded URL, opens share sheet
- [ ] `vote.html` on GitHub Pages renders the shortlist nicely on mobile
- [ ] Page has App Store / "search Zonnie" CTA

## Feature 3 — Golden Hour pushes

**What:** Two notification types:
1. **Weekly best-window:** "☀️ Saturday 15:00–18:00 is the best terrace window this
   week" — computed from the existing forecast data.
2. **Favourite alert (already designed, Pro):** "Café Kiebêrt hits 90 in ~1 hour."

**Why:** Retention. The difference between remembered and deleted.

**Implementation notes:**
- Push infra is already built & gated (per project docs: "Push notifications (built,
  gated)"). **Audit `src/` for the existing notification scheduling code before
  writing anything new.**
- Weekly best-window: schedule a **local** notification (no server needed) via
  `expo-notifications` local scheduling. Compute the window when the app is opened
  (piggyback on the existing weather fetch), schedule/replace one local notification
  for the upcoming weekend. **Confirm `expo-notifications` is in the installed
  binary**; it should be since the feature is "built, gated". If yes → OTA-shippable.
- Tier split: weekly best-window = FREE (acquisition/retention). Per-favourite
  alerts = PRO (existing plan, keep).
- Settings toggle in whatever settings UI exists; default ON for the weekly one with
  a polite first-run prompt (respect iOS permission flow — ask in context, not at
  launch).
- Copy tone: short, warm, zero corporate. The examples in this doc are final copy.

**Acceptance:**
- [ ] Weekly window computed + local notification scheduled/replaced on app open
- [ ] Respects permission state; one contextual permission ask max
- [ ] Settings toggle
- [ ] Favourite alerts remain Pro-gated

## Feature 4 — Zonnie Wrapped (seasonal; build groundwork now, ship September)

**What:** End-of-season recap: hours of terrace sun caught, top neighbourhood,
most-visited terrace, shareable card set (reuse the Feature 1 renderer).

**Why:** Identity + screenshot moment exactly when seasonal deletion risk peaks.

**Implementation notes — data collection starts NOW:**
- We can't show a recap without history. Add a lightweight local "sun log":
  - On explicit interactions (favouriting, opening a terrace detail, tapping
    directions), append `{date, terraceId, scoreAtTime}` to a persisted Zustand store
    (`src/store/sunLogStore.ts`, persisted like the existing stores).
  - Privacy: all local, no server. State this in the recap UI when built.
- The Wrapped UI itself is a September task; this PR only ships the logging +
  a hidden debug screen to inspect the log.
- v1 uses absolute stats only ("43 hours of sun", "12 terraces visited",
  "most-visited: …"). **No fake percentiles** — we have no server data to support them.

**Acceptance:**
- [ ] sunLogStore persists events, capped (e.g. 2,000 entries, FIFO)
- [ ] Zero new permissions requested
- [ ] Debug screen behind long-press on version number (or similar)

## Feature 5 — Hidden Gems mode → make it FREE

**What:** Re-rank toggle: sunny AND not tourist-rammed. Per existing design docs this
was planned as Pro-exclusive ("Hidden Gem mode: sun + inverse busyness + rating").

**Why flip to free:** it's the insider-knowledge feature young locals show friends at
the table. The flex is the marketing. Keep the time scrubber as the Pro hook (it
already converts).

**Implementation notes:**
- v1 proxy for "busyness" (no live busyness data exists):
  - Google rating count percentile (very high count ≈ touristy) — already fetched via
    Places (`src/data/places.ts`, `placesStore`),
  - distance from Centrum centroid (closer ≈ touristier),
  - neighbourhood weighting (small hardcoded table: Centrum/Red Light heavily
    touristy → De Pijp/Oost/Noord less so).
  - `gemScore = sunScore * 0.6 + (1 - touristProxy) * 0.25 + ratingNorm * 0.15`
- UI: a "💎 Hidden gems" chip in the WHAT card row 2
  (`src/components/VenueTypeFilter.tsx`), styled like the existing mode chips
  (Outdoor Screen = burnt, Near me = leaf — use mustard for gems).
- Paywall integrity: REMOVE Hidden Gems from any Pro marketing copy if present.
  Only advertise what's real; never advertise as paid what is free.

**Acceptance:**
- [ ] Gems chip toggles re-rank in list + map
- [ ] No Pro gate
- [ ] Ranking sane on spot-check (Centrum tourist traps demoted)

## Micro-feature (bundle with Feature 1) — Sundowner countdown

On the terrace detail sheet, if sun leaves the terrace within 90 min:
`"☀️ Sun leaves this terrace in 40 min"` — amber pill, computed from the existing
hourly timeline (first upcoming hour where score drops below 30). Creates urgency;
it's the fact someone announces to the table. ~30 lines of code.

## Explicitly OUT of scope (do not build)

- UGC photo feeds, comments, check-in streaks, accounts/social graph — needs critical
  mass the app doesn't have, invites moderation burden, and a half-empty social feed
  reads as failure.
- Any fake data: no fake percentiles, no fake busyness claims (label the gems proxy
  "estimated" if surfaced to users).
- Anything requiring a new native module without flagging the PR "requires new binary".
